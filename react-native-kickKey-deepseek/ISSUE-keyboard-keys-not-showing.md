# Issue: Keyboard shows blank area but no keys (EAS production build)

> **Reported:** 2026-07-30
> **Status:** 🔧 **Fixed** — fix applied 2026-07-31 (see §11); re-test with a fresh EAS build
> **Build:** `eas build --platform android --profile production` (APK, release)
> **Build result:** ✅ `BUILD SUCCESSFUL in 11m 16s` (449 tasks)

---

## 1. Summary

After installing the **production** APK built with EAS, the companion app opens
fine and the user **can** enable KickKey as the default keyboard. However, when
focusing any text input field, the keyboard takes up the expected on-screen
area, but **no keys are rendered** — the keyboard is blank.

Because the IME window **does** appear with the correct height, the native side
(IME service registration, `onCreateInputView`, the container view) is working.
The blank content points at the **React surface inside the IME process failing
to render**, i.e. the **keyboard JS bundle (`keyboard.bundle`) is either missing
from the APK, not loadable by Hermes, or crashing at startup** — all of which
produce exactly this symptom.

## 5. Architecture background

Two separate React Native bundles ship in the same APK:

1. **Companion app bundle** — `expo-router/entry.js` (gradle task
   `createBundleReleaseJsAndAssets`). Runs in the main process. **This works.**
2. **Keyboard bundle** — `keyboard.index.js` → `keyboard.bundle` (Hermes
   bytecode, ~1.2 MB). Generated by `plugins/withKeyboardBundle.js` **during
   `expo prebuild`**, written to `android/app/src/main/assets/keyboard.bundle`,
   then packaged into the APK as an asset.

At runtime the IME process (`KickKeyApplication`, `:ime_process`) lazily builds
a second `ReactHostImpl` whose delegate loads:

```kotlin
JSBundleLoader.createAssetLoader(this, "assets://keyboard.bundle", true)
```

`KickKeyInputMethodService.onCreateInputView()` then creates a Fabric
`ReactSurface` for the component `KickKeyKeyboard`. The surface's host is
`ReactHostImpl(..., useDevSupport = ReactBuildConfig.DEBUG /* false in release */)`.

**Failure of any step in that chain produces a blank keyboard area**, because
`onCreateInputView` still returns a `FrameLayout` with `minimumHeight = 770px`
even when the React content inside never renders.

## 6. Root-cause hypotheses (ranked)

### H1 — `keyboard.bundle` is missing from the production APK *(most likely)*
The `withKeyboardBundle` plugin either did **not** run during the EAS prebuild,
or ran but its output was not packaged, so `assets://keyboard.bundle` does not
exist in the APK. The IME process has no JS to execute → blank surface.

How it could happen:
- EAS prebuild step failing/skipping the plugin silently (plugin errors during
  prebuild are not visible in the gradle step).
- **EAS Build caches the prebuild result** — a cached prebuild from an earlier
  build (before `withKeyboardBundle` existed or produced a valid bundle) could
  be restored, shipping an APK whose `keyboard.bundle` is stale or absent.
- The plugin's `execSync("npx react-native bundle ...")` failing on the EAS
  Linux worker (e.g., CLI resolution) — if it failed, the plugin throws
  FATAL and the *prebuild* would fail; since the overall build succeeded, the
  plugin most likely ran, which makes this hypothesis somewhat less certain
  (see H2/H3 for the runtime-side alternatives).

**Confirm:** inspect the APK — see §7 step 1. If `keyboard.bundle` is absent,
this is the root cause.

### H2 — `keyboard.bundle` present but Hermes rejects it at runtime
The bundle is packaged but Hermes can't load it, e.g.:
- Bytecode version mismatch (compiled with a different `hermesc` than the
  runtime Hermes). Local file is v98; if the EAS worker resolved a different
  `hermesc` (e.g., a PATH `hermesc` instead of `hermes-compiler`), the version
  could differ and Hermes would refuse to load it.
- The asset got packaged as plain JS (plugin's "stale plain-JS" case) and
  `JSBundleLoader`/Hermes can't run it.

**Confirm:** check bytecode version of the bundle inside the APK (§7) and
logcat for `KickKeyApplication` "Failed to init keyboard ReactHost" /
"bytecode version" errors.

### H3 — Bundle loads, but the keyboard JS crashes during startup
The bundle executes but throws before/while mounting `KeyboardScreen` in the
IME process (module-scope error, missing native module, Fabric/surface issue in
release). The `ErrorBoundary` should surface render errors as visible text —
but errors thrown *before* React mounts, or a failed `ReactHostImpl.start()`,
only log to logcat and leave the surface blank.

**Confirm:** `adb logcat` while opening the keyboard — look for
`KickKey JS FATAL`, `KickKey ErrorBoundary`, `KickKeyIME`,
`KickKeyApplication`, `ReactNativeJS` lines (§7 step 2).

### H4 — Surface/view wiring issue in release Fabric
`host.createSurface(this, "KickKeyKeyboard", null)` + `surface.start()` +
immediate `surface.view` — if the surface view is created but never attaches or
renders content in the release build, the container shows empty area. Lower
likelihood (the same code path is used in debug), but worth ruling out via the
diagnostics below.

## 7. Diagnostics (how to confirm)

Run these against the failing production APK / device:

1. **Check the APK for the keyboard bundle asset**
   ```sh
   unzip -l app-release.apk | grep -i keyboard
   # or
   aapt list app-release.apk | grep -i keyboard
   ```
   Expected if healthy: `assets/keyboard.bundle` (1.2 MB). If missing → H1
   confirmed.

2. **Check the bundle's bytecode version inside the APK**
   ```sh
   # Simplest — prints: "Hermes JavaScript bytecode, version 98"
   unzip -p app-release.apk assets/keyboard.bundle > /tmp/kb.bundle && file /tmp/kb.bundle

   # Raw hex (magic is 8 bytes: c6 1f bc 03 c1 03 19 1f; version is a
   # ULEB128 int after it — 0x62 = 98)
   unzip -p app-release.apk assets/keyboard.bundle | xxd -l 16
   # portable alternative if xxd is unavailable:
   unzip -p app-release.apk assets/keyboard.bundle | od -A x -t x1z -l 16
   ```
   Expect `file` to report version **98** (matching the local bundle and
   `hermes-compiler`). Any other version → H2 bytecode mismatch.

3. **Logcat while opening the keyboard** (IME process)
   ```sh
   adb logcat -s KickKeyIME KickKeyApplication KickKeyModule ReactNativeJS AndroidRuntime
   # or filter broadly:
   adb logcat | grep -E "KickKey|ReactNative|ReactNativeJS|AndroidRuntime"
   ```
   Look for:
   - `Keyboard ReactHost initialized successfully — JS bundle loaded...` (host OK)
   - `Failed to init keyboard ReactHost synchronously` / `keyboard.bundle ... corrupt` (H1/H2)
   - `KickKey JS FATAL ...` / `KickKey ErrorBoundary ...` (H3)
   - `FALLBACK VIEW SHOWN: ...` (means `onCreateInputView` fell back to error UI)

4. **Re-check the EAS prebuild step logs** (not the gradle step) for
   `[withKeyboardBundle]` lines:
   ```
   [withKeyboardBundle] Step 1/2: Building keyboard JS bundle via Metro...
   [withKeyboardBundle] ✅ Bundle format: Hermes bytecode
   [withKeyboardBundle] ✅ Final size: ... KB
   ```
   Absence of these lines in the prebuild step → the plugin never ran → H1.

5. **Test a debug/local build for comparison** — `npm run android` (debug) and
   `expo prebuild` locally already produce a valid v98 bundle; if debug works
   and release doesn't, the difference is the EAS prebuild/packaging path.

6. **Verify the plugin works with the current toolchain locally** — run
   `npx expo prebuild --clean` and watch for the `[withKeyboardBundle]`
   console lines (Step 1/2 Metro, Step 2/2 hermesc, ✅ Hermes bytecode). If
   the plugin logs those locally but the EAS prebuild step shows no such
   lines, the EAS-side prebuild is the problem (H1).

## 8. Candidate fixes (once confirmed)

- **If H1 (asset missing):** Make keyboard-bundle generation **robust in the
  EAS pipeline**:
  - Add a `prebuild` hook / EAS `eas.json` step that runs
    `npm run build:keyboard` (`scripts/build-keyboard-bundle.js`) **before**
    gradle, so `keyboard.bundle` is guaranteed to exist in
    `android/app/src/main/assets/` at merge time; or
  - Convert the keyboard bundling into a **gradle task**
    (`createKeyboardBundleReleaseJsAndAssets`) mirroring
    `createBundleReleaseJsAndAssets` for the main bundle, so it runs inside
    `assembleRelease` on the EAS worker with the same Metro/Hermes toolchain.
- **If H2 (bytecode mismatch):** Pin/verify `resolveHermesc` resolves the
  `hermes-compiler` binary (v98) on the build worker; add a bytecode-version
  check in the plugin and fail loudly on mismatch instead of shipping a blank
  keyboard.
- **If H3 (JS crash):** Wrap `keyboard.index.js` startup in try/catch, log
  module-scope errors to logcat, and add a visible fallback if
  `ReactHostImpl.start()` fails; verify `NativeModules.KickKey` is available in
  `:ime_process` before `KeyboardScreen` mounts.
- **All cases:** Add a runtime self-check in `KickKeyInputMethodService` that
  verifies `assets://keyboard.bundle` is readable before creating the surface,
  and show a clear error string instead of a silent blank area.

## 10. Quick verdict

The gradle log is clean and the companion app works, so the failure is
**specifically the keyboard JS bundle not rendering inside the `:ime_process`**.
The highest-probability cause is that `keyboard.bundle` is **missing or
unloadable in the production APK** because it is produced by a prebuild-time
config plugin whose output must be verified inside the actual APK. Confirm with
§7 steps 1–3 (APK asset check + logcat), then apply the matching fix from §8.

## 11. Fix applied (2026-07-31)

Two changes were made to eliminate the silent blank keyboard:

### 11.1 Gradle task — bundle is (re)built inside `assembleRelease`

**`plugins/withKeyboardBundle.js`** now uses `withAppBuildGradle` to inject a
Gradle task `createKeyboardBundleReleaseJsAndAssets` into
`android/app/build.gradle`. The task:

- Runs `node scripts/build-keyboard-bundle.js` (Metro → `hermesc` HBC v98)
  before `mergeReleaseAssets` / `mergeDebugAssets`,
- Declares proper `inputs`/`outputs` so Gradle can up-to-date check it,
- **Fails the build loudly** (`GradleException`) if
  `android/app/src/main/assets/keyboard.bundle` is missing or `< 100` bytes,
  instead of shipping a blank keyboard.

This makes keyboard-bundle generation independent of EAS prebuild caching or
plugin execution: the bundle is always rebuilt on the EAS worker with the same
Metro/Hermes toolchain as the main bundle.

### 11.2 Runtime self-check — visible error instead of blank area

**`native-files/java/com/kickkey/KickKeyInputMethodService.kt`** now calls
`verifyKeyboardBundle()` at the top of `onCreateInputView()`:

- Verifies `assets://keyboard.bundle` exists,
- Verifies the 4-byte Hermes magic (`C6 1F BC 03`),
- Returns a **visible fallback error view** (dark background + message) with a
  clear reason (`MISSING`, `truncated`, `not Hermes bytecode`, `unreadable`)
  instead of a silent transparent area.
